# 《VibeGame》联机系统设计

> **文档状态**：草案 v0.2  
> **Layer**：Foundation
> **Priority**：MVP  
> **关联总案**：[`../游戏粗略策划案.md`](../游戏粗略策划案.md)  
> **Quick reference**：关键依赖 战斗系统、冒险系统、状态效果系统

## Summary

联机系统以房主权威模型承接多人合作玩法的同步需求，负责「如何同步」而非「规则是什么」。它同步房间、冒险节点选择、战斗操作与结果广播，不反向定义战斗或奖励规则。

## 1. 文档定位

本文件是联机系统的主文档，负责说明联机系统在整个项目中的职责边界，以及联机系统如何承接其他玩法系统的同步需求。

本文件负责：

- 联机系统的设计目标与边界。
- 权威模型与同步职责划分。
- 房间、连接、战斗同步的抽象关系。
- 与详细技术方案文档的对应关系。

本文件不负责：

- 具体网络库、传输层和实现细节的全部展开。
- 单个战斗机制的玩法规则定义。

## 2. 玩家体验目标

- 让多人合作玩法拥有稳定、可扩展、可验证的同步边界。
- 让玩法系统的结算仍以单一权威端为准，避免多人不同步带来的规则歧义。
- 让联机系统成为承接玩法系统的技术层，而不是反向定义玩法规则。
- 房主权威：房主负责战斗结算，其它玩家提交操作请求，战斗规则仍由单一逻辑源决定。

## 3. 详细设计

### 3.1 核心规则

#### 当前联机方向

- 当前采用多人合作对抗敌方阵营的方向。
- 房主承担服务器功能，作为权威结算端。
- 普通客户端以发送操作请求和接收结果广播为主。

#### 同步边界

联机系统应重点承接以下同步对象：

- 房间与玩家加入离开。
- 冒险节点选择结果。
- 战斗中的操作请求顺序。
- 战斗状态快照与关键事件广播。
- 奖励结果与章节推进结果。

#### 玩法系统与联机系统解耦

联机系统只负责「如何同步」，不负责「规则本身是什么」。例如敌方意图如何生成、地形如何反应，仍应由对应玩法系统文档定义。

### 3.2 状态与流转

| 状态 | 进入条件 | 退出条件 | 行为 |
| --- | --- | --- | --- |
| 未连接 | 启动游戏 | 加入或创建房间 | 仅本地菜单 |
| 房间中 | 加入房间成功 | 开始冒险或解散 | 同步玩家列表与准备状态 |
| 冒险中 | 冒险流程开始 | 本局结束 | 同步节点选择与章节推进 |
| 战斗中 | 进入战斗节点 | 战斗结算完成 | 同步操作请求与权威结算结果 |

### 3.3 与其他系统的交互

| 类型 | 主要内容 |
| --- | --- |
| 上游依赖 | 战斗系统、敌人系统、状态效果系统、冒险系统、奖励系统 |
| 系统产出 | 房间连接、操作请求、状态同步、事件广播、战斗结果分发 |
| 下游影响 | 玩家看到的战斗表现顺序、多人行动一致性、房主权威结算体验 |

## 4. 边界情况

- **若表现层动画导致客户端短暂不同步**：以战斗结算层最终顺序为准（见战斗系统共享玩家回合规则）。
- **若未来从房主权威转向专用服务器**：需单独重写联机系统边界，本文档失效。
- **联机系统不应成为玩法规则的第一定义处**：任何玩法争议应回到对应 机制层文档裁决。

## 9. 验收标准

- **GIVEN** 两名玩家在同一房间且房主在线，**WHEN** 非房主提交战斗操作，**THEN** 房主权威端按收到顺序结算并广播一致结果。
- **GIVEN** 冒险层完成节点选择，**WHEN** 所有客户端同步该结果，**THEN** 各客户端进入相同类型的下一节点。
- **GIVEN** 联机文档与战斗规则对同一时序有不同描述，**WHEN** 发生冲突，**THEN** 以战斗系统 机制层文档为准，联机仅负责同步该规则的结果。
