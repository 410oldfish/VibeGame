# VibeGame 程序开发指导

> 文档状态：程序规范草案 v0.1  
> 维护位置：`design/程序/程序开发指导.md`  
> 适用范围：Unity 客户端、战斗原型、TEngine 集成、联机同步与后续系统扩展。  
> 核心目标：让程序实现持续贴合策划系统边界，并逐步收束到 TEngine 的模块化开发方式。

## 1. 项目理解

VibeGame 是一款以六边形战场为核心的多人合作卡牌 Roguelike。玩家在章节路线中推进，通过卡牌构筑、职业成长、状态效果、地形改装和队友配合，在可预判的敌方意图压力下完成战斗。

当前项目的四个核心玩法支柱是：

- 位置与移动：体力、路径、距离、击退、拉拽、占位和危险落点应成为每回合的重要决策。
- 卡牌与构筑：牌组成长服务职业战术身份，而不是只堆叠伤害数字。
- 敌方牌局：敌人也有牌组、抽牌、弃牌、公开意图和可被干涉的行动节奏。
- 地形改写：地形可以被生成、覆盖、转化、破坏、推动和引爆，并与状态、移动、敌方意图联动。

首个原型应优先验证六边形移动、敌方公开意图、少量地形改装、三职业精简牌组和房主权威同步，不应过早扩展大量内容。

## 2. 架构总原则

1. 以 TEngine 为项目程序架构基准。
2. 新系统优先设计为 `Interface + Module`，并通过 `HexGameModule` 暴露访问入口。
3. 模块间通信优先使用 `GameEvent`，避免控制器互相硬引用。
4. 玩法规则优先落在领域模型、Resolver、State、Service 中，表现层只负责展示和输入。
5. 联机下真实结算只发生在 Host 权威端，客户端只提交请求和播放结果。
6. 代码应贴合策划系统边界：战斗、卡牌、职业、敌人、地形、状态、奖励、冒险、联机各自有清晰职责。
7. 小步演进现有代码，不为“纯净架构”一次性重写可运行原型。

## 3. TEngine 使用规则

### 3.1 模块访问

- 项目业务代码通过 `HexGameModule` 访问 TEngine 或自定义模块。
- 不在业务代码中直接调用 `ModuleSystem.GetModule<T>()`，除非正在实现 `HexGameModule` 或框架集成层。
- 新增模块时，优先放在 `Assets/Scripts/TEngineIntegration` 或清晰的系统目录中，并注册为 TEngine `Module`。

推荐模式：

```csharp
public interface IHexBattleModule
{
    void StartBattle(...);
}

public sealed class HexBattleModule : Module, IHexBattleModule
{
    public override void OnInit() { }
    public override void Shutdown() { }
}
```

然后在 `HexGameModule` 暴露：

```csharp
public static IHexBattleModule Battle => _battle ??= Get<IHexBattleModule>();
```

### 3.2 更新驱动

- 不随意新增 `MonoBehaviour.Update()`。
- 原型中已有 MonoBehaviour 可保留，但新增持续更新逻辑优先挂到 `HexGameModule.Update.AddUpdateListener`。
- 记得在销毁时移除监听，避免残留回调。

### 3.3 事件系统

- 跨模块通知使用 `GameEvent.Send(...)`。
- UI 或视图侧监听事件时必须考虑生命周期清理。
- 现阶段项目使用 int 常量事件，新增事件统一写入 `HexGameEvents`。
- 后续若启用 TEngine Source Generator，可将稳定的跨模块事件迁移为接口事件。

事件命名建议：

- `BattleStarted`
- `BattleFinished`
- `BattleStateChanged`
- `EnemyIntentChanged`
- `AdventureNodeSelected`
- `RewardChosen`

### 3.4 资源规则

- 运行时资源加载优先使用 TEngine Resource/YooAsset 体系。
- 避免在运行时代码中扩散 `Resources.Load`、`AssetDatabase.LoadAssetAtPath`。
- `AssetDatabase` 只用于 Editor 工具或明确的编辑器原型路径，并用 `#if UNITY_EDITOR` 包裹。
- 动态加载资源必须有释放策略；GameObject 资源优先走自动引用管理方式。

### 3.5 UI 规则

- 新 UI 优先考虑 TEngine `UIWindow/UIWidget` 生命周期。
- 现有原型 UI 如 `HexBattleUI`、`HexAdventureController` 中的运行时拼 UI 可继续维护，但新增复杂界面应逐步迁移成窗口/组件。
- UI 不直接定义玩法规则，只读取状态、发送操作请求、响应事件。
- UI 中的卡牌、状态、敌人意图、地形预览应尽量由数据驱动。

## 4. 玩法系统边界

### 4.1 战斗系统

负责：

- 战斗进入、开始、回合推进、胜负判断和战斗结果出口。
- 玩家阵营回合与敌方阵营回合的公共时序。
- 卡牌、移动、状态、地形、敌人意图的统一结算承载。

不负责：

- 奖励内容本身。
- 冒险地图节点生成。
- 单职业完整牌表。
- 网络传输细节。

程序建议：

- 中长期拆分为 `BattleState`、`BattleResolver`、`TurnResolver`、`CardResolver`、`MovementResolver`、`StatusResolver`、`TerrainResolver`。
- 当前 `HexBattleController` 可以作为原型编排器，但新规则应尽量抽到独立方法或服务类，避免继续膨胀。

### 4.2 六边形空间系统

负责：

- 六边形距离、邻接、路径、范围、占位、主动移动、被动移动和冲突处理。

程序建议：

- 路径和范围计算保持纯逻辑，方便 Host 验证、快照同步和自动测试。
- 主动移动和被动位移必须区分：主动移动消耗体力并受每回合次数限制，被动位移不消耗体力但触发地形和碰撞。
- 强制位移、撞墙、深坑、挤出单位等应统一走 MovementResolver，而不是散落在卡牌效果里。

### 4.3 卡牌与构筑系统

负责：

- 抽牌堆、手牌、弃牌堆、消耗牌堆。
- 卡牌费用、目标、范围、关键词、临时牌和战斗结束清理。
- 玩家构筑成长方向。

程序建议：

- 卡牌定义数据和卡牌实例状态分离。
- 卡牌效果不应长期依赖中文名称 `switch`；可先保留原型实现，但新增卡牌应逐步转为 ID、效果类型、参数和效果解释器。
- 每张牌应可标注五维：输出、生存、移动、费用、抽牌运转，便于奖励筛选和平衡统计。

### 4.4 职业系统

负责：

- 初始属性、关键词、核心技能、初始牌组、成长方向和职业奖励池。

当前职业身份：

- 战士：输出与移动压迫，武器切换、冲撞、流血、自伤转换。
- 骑士：生存与防线护卫，格挡、净化、反击、嘲讽、队伍保护。
- 德鲁伊：形态切换与地形异常，猛犸、蟾蜍、火山鬣蜥、大王花。

程序建议：

- 职业数据应逐步数据化，避免职业规则散落在多个控制器内。
- 职业技能走统一请求与结算流程，联机时房主验证后执行。

### 4.5 敌人系统

负责：

- 敌方牌组、抽牌、弃牌、公开三牌意图、执行失败去向和抽空牌堆增益。

程序建议：

- 敌人不是固定技能循环，应拥有自己的牌组状态。
- 战斗开始时先生成第一轮公开意图，再进入玩家先手。
- 敌方意图应作为同步数据进入 Snapshot，作为 UI 和玩家决策依据。
- 玩家对敌方牌局的干涉应改变敌方牌区或意图，而不是只改动画表现。

### 4.6 地形系统

负责：

- 基础地面、构筑物、临时覆盖三层结构。
- 地形生成、覆盖、转化、破坏、推动、引爆。
- 通行限制、落点价值、环境伤害和区域收益。

程序建议：

- 单格地形状态应分层建模，避免把所有地形都塞成一个 enum。
- 地形反应应走统一规则表或 Resolver，例如水域通电、火焰融冰、毒雾引爆。
- 地形必须保证可读、可预览、可同步，并避免永久封死战场。

### 4.7 状态效果系统

负责：

- 增益、减益、技能、道具跨系统语义。
- 回合开始、受伤时、攻击时、移动时、回合结束等时机点。

程序建议：

- 状态词条数据和状态结算语义分离。
- 关键状态如圣盾、格挡、无敌、冰冻、束缚、稳固、燃烧、感电等应由统一时机处理。
- 受伤流程必须有明确顺序：免伤/无敌/冰冻、圣盾、减伤、护甲、生命、反伤/触发等。
- 若规则影响敌方意图，应明确是影响当前已公开意图，还是只影响下一次生成。

### 4.8 冒险、奖励与遭遇

冒险系统负责章节路线、节点选择和战斗入口；奖励系统负责战斗后成长、商店、事件与休息；遭遇系统负责教学、检验和内容编排。

程序建议：

- 冒险节点选择在多人下应由房主权威确认并广播。
- 奖励三选一、商店、休息等服务应输出明确的状态变化事件。
- 遭遇配置应逐步数据化，避免硬编码敌人数量、出生点和奖励。

## 5. 联机开发规则

当前目标是 Steam PC，多人合作，房主 Host 权威，不自建专用服务器。

核心同步模型：

```text
ActionRequest -> Host Validate -> Host Resolve -> BattleEvents -> Snapshot
```

规则：

- 普通客户端只发送操作请求，不直接修改真实战斗状态。
- 房主玩家也必须走同一套请求流程，不能通过本地 UI 直接改状态。
- 所有随机数由 Host 产生，包括抽牌、奖励、地图节点、敌人意图、商店商品等。
- 每次关键操作后广播 BattleEvents，并在关键节点同步 Snapshot 校正表现。
- 不把每张卡牌、每个 Buff、每个 UI 手牌对象做成 NetworkObject。
- 网络层只负责同步边界，不反向定义玩法规则。

优先同步对象：

- 房间玩家、职业选择、准备状态。
- 冒险节点选择结果。
- 操作请求顺序。
- 战斗事件流。
- 战斗状态快照。
- 奖励选择和章节推进结果。

## 6. 数据与配置原则

- 稳定规则代码化，内容条目数据化。
- 卡牌、敌人牌、职业初始配置、遭遇、地形模板、奖励池都应逐步迁移到配置数据。
- 配置字段应使用稳定 ID，不依赖中文显示名作为规则分支。
- 中文名称只用于显示、策划阅读和调试日志。
- 配置和运行时状态分离，避免战斗中修改原始定义。

建议 ID 格式：

```text
card_warrior_slash_001
status_holy_shield
terrain_fire
enemy_goblin_basic
profession_paladin
```

## 7. 代码组织建议

当前已有目录：

```text

Assets/Scripts/HexDemo
Assets/Scripts/Battle

```

后续建议逐步收束为：

```text
Assets/Scripts/Battle
  State
  Resolver
  Events
  Snapshot
  Random
  View
Assets/Scripts/Adventure
Assets/Scripts/Card
Assets/Scripts/Profession
Assets/Scripts/Terrain
Assets/Scripts/Status
Assets/Scripts/Reward
Assets/Scripts/Network
Assets/Scripts/TEngineIntegration
```

迁移策略：

- 短期不强拆可运行原型。
- 每次新增规则时，优先抽出纯逻辑类或服务类。
- 每次修复旧逻辑时，顺手减少中文名硬编码、UI 与规则耦合、客户端与权威逻辑耦合。

## 8. 验证与测试规则

每次玩法改动至少确认：

- 是否破坏战斗回合时序。
- 是否影响 Host 权威同步边界。
- 是否需要加入 BattleEvent 或 Snapshot 字段。
- 是否需要 UI 预览或敌方意图展示。
- 是否有随机数，若有必须由 Host 产生。
- 是否有状态时机，若有必须明确结算顺序。
- 是否有地形/位移，若有必须经过路径、占位和冲突规则。

原型测试应优先记录：

- 每回合玩家移动格数与剩余体力。
- 地形改装牌选择率和有效收益。
- 敌方公开意图是否足够清楚。
- 地形/位移击杀占比。
- 合作模式中堵位、等待和误伤问题。
- 五维统计：输出、生存、移动、费用、抽牌运转的实际发生频率。

## 9. 开发红线

- 不让 UI 成为玩法规则源。
- 不让网络层定义玩法规则。
- 不让客户端产生真实随机数。
- 不让中文显示名成为长期规则 ID。
- 不把临时效果永久写入局外数据，除非策划明确要求。
- 不把所有状态效果继续堆进单个巨型方法，新增复杂状态应抽出结算时机。
- 不为了架构洁癖打断可玩原型，但也不继续扩大不可维护的硬编码。

## 10. 当前优先级

1. 保持现有原型可运行。
2. 修正战斗核心规则与状态结算的一致性。
3. 将卡牌、状态、敌人意图和地形逐步从硬编码转向数据驱动。
4. 完成 Host 权威的 ActionRequest、BattleEvents、Snapshot 骨架。
5. 让三职业在六边形、地形和敌方意图中表现出明确身份。
6. 用少量遭遇验证系统，而不是堆内容。
